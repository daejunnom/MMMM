# MMMM 검증·테스트 판정 보완

이 문서는 [구현 기준](ENGINEERING-STANDARDS.md)의 검증·테스트 원칙을 보완한다.
[기여 절차](../CONTRIBUTING.md)와 [빌드 수명](build-system.md)의 기존 규칙은 유지한다.

## 계약을 관찰하는 assertion

검사는 보호할 입출력, 상태 전이 또는 불변식을 직접 관찰한다. private 필드명,
컨테이너 종류, 구현 문장의 배치나 다른 테스트의 assertion 문자열을 동작의 대용으로
고정하지 않는다. 내부 불변식을 확인하는 white-box 검사는 허용하되, Java 예약 상태를
reflection으로 읽어 특정 `Map`에 캐스팅하는 식의 구현 형태 의존은 계약 관찰과 구분한다.
실제 의존 방향, ABI, wire 형식처럼 구조 자체가 계약인 검사는 유지한다.

인수 항목의 충족은 의미 있는 사례와 관측 결과로 확인한다. 전체 테스트 수나 소스의
마커 존재만으로 필요한 검사가 수행됐다고 판정하지 않는다. 반대로 정본에서 정한
필드 수, 명령 순서, 수학적 기대값과 정확한 인수 대상은 단순 개수 검사로 취급해 없애지 않는다.
중복 proxy 검사의 정비를 위해 새로운 검사기 검증 계층이나 별도 등록부를 만들지 않는다.

## fixture와 거절 경로의 독립성

fixture의 입력과 초기 상태는 검사하려는 계약의 전제를 만족해야 한다. 의도한 거절
조건보다 앞선 다른 오류로 실패한 실행은 그 거절 검사의 성공이 아니다. 기존 검사 안에서
실제 오류 종류와 발생 경계, 계약이 요구하는 상태 보존 또는 효과 부재를 확인한다.
임의의 예외, 비영 종료 또는 출력 부재만으로 서로 다른 거절 원인을 모두 통과시키지 않는다.

HostRuntime의 읽기 사전 조건 확인과 실제 쓰기 권한 요청, 대상 API 호출, 상태 변경을
구분해 관찰한다. 사전 검사 호출 자체를 mutation으로 간주하거나, 사전 검사 성공만으로
효과가 없었다고 판정하지 않는다. 변경된 계약에 맞춰 fixture를 고칠 때도 제품의 권한,
revision, dispatch 및 readback 검사를 우회해 입력을 유효하게 만들지 않는다.

기대값은 검사 대상 구현의 출력에 맞춰 자동 갱신하지 않는다. 적용 경로와 관찰 oracle이
같은 잘못된 변환을 공유하지 않도록 하고, 실패를 없애기 위한 기대 오류 코드 교체나
assertion 완화는 계약 근거 없이 수행하지 않는다.

## 테스트 전용 기능의 경계

테스트 전용 동작과 의존성은 Rust의 `cfg(test)`·test target 및 JVM의 test source set 등
테스트 계층에 둔다. 테스트 통과만을 위해 제품에 숨은 옵션, 환경 변수 우회 분기,
테스트 전용 상태 노출 API나 다른 실행 알고리즘을 추가하지 않는다. 기존 application port와
테스트 fixture를 사용하며 제품의 입력 검사와 정당한 운영 진단을 테스트 편의 기능과 구분한다.

fake host, fault injection과 기대값 계산이 실제 호스트 승인·관측 자료를 발급하는 경로에
섞이거나 제품 배포 산출물의 운영 경로로 연결되지 않게 한다. 관찰을 쉽게 만들기 위해
검사 대상의 권한·스레드·소유권·수명 경계를 다른 경로로 대체하지 않는다.

## 실행 결과 판정

테스트 runner는 종료 결과를 실제 호출한 자식 프로세스에 귀속시킨다. PowerShell의 이전
`$LASTEXITCODE`·`$?`를 현재 bootstrap의 결과로 읽거나, 예상한 거절을 처리했다는 이유로
이후 assertion 실패까지 성공으로 덮지 않는다. JVM 보고서 판정에서는 XML 요소명과
`name` 속성을 구분한다. 보고서 해석·내보내기 실패와 실제 테스트 실패는 원인을 분리해
남기며, 해석 실패를 빈 성공 결과로 채우지 않는다.

## CI 병렬화와 로컬 실행 분리

CI의 독립 검사군은 격리된 runner/job으로 나누어 검사끼리의 CPU·메모리·프로세스 경합을
줄인다. 한 runner에서 compiler, 테스트 프로세스와 제품 worker를 무조건 동시에 늘리는
방식을 병렬화의 기본으로 삼지 않는다. 기존 실행 시간과 자원 관측을 참고해 긴 shard의
편중, 마지막 job의 완료 지연과 지나친 분할에 따른 환경 준비 비용을 함께 줄인다.

순수 Rust 검사, JVM 검사와 native 호스트 연동 검사는 실제 의존 관계에 따라 배치한다.
하나의 연동 시나리오에 필요한 준비·적용·readback·종료 순서는 분할하지 않는다. 병렬화
뒤에도 필요한 target과 사례가 실제 실행되고 결과 집계에 빠짐없이 연결되도록 하며,
다른 job의 로그·보고서 덮어쓰기나 누락 결과의 성공 처리를 허용하지 않는다.

로컬은 CI와 같은 독립 호스트 격리를 가정하지 않는다. 동일 Store·CAS·Coordinator,
포트·전역 상태·관리 lease를 공유하는 검사는 기존 소유 슬롯과 수명 규칙 안에서 분리하고,
안전한 분리가 어려운 해당 검사군만 직렬화한다. 제품의 동시성·경합을 검증하는 시나리오
내부까지 직렬화하거나 제품 worker·자원 한도·assertion을 낮춰 테스트 간 경합을 숨기지 않는다.
